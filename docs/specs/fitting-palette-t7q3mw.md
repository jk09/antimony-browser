## 2. Summary

- **Problem statement:** The browser UI has one light and one dark palette, picked by the OS. Users with astigmatism, light sensitivity, low vision, dyslexia or colour-vision deficiency can't adapt it, and don't know which colours would help.
- **Desired outcome:** The user says what they need in their own words. The model proposes 3–4 themes using usability guidance; Antimony makes sure each meets WCAG 2.2 AA contrast, shows each as a real screenshot of the browser, and applies the chosen one. The same flow, and the other welcome choices, can be changed later with `/settings`.

## 3. Background and Context

- **Current behavior:** Colours are CSS custom properties on `:root` (`--toolbar-bg`, `--panel-bg`, `--text`, `--muted`, `--field-bg`, `--field-border`, `--card-bg`, `--card-border`, `--accent`, `--accent-text`, `--hover`, `--focus`, `--error`, `--ok`, `--code-bg`, `--cloud-0…4`) with a `prefers-color-scheme: dark` override. The welcome page (spec first-light-w5k8rd) sets up the CLI and model. Settings are changed with separate commands (`/model`, `/page-access`, `/history-access`).
- **Motivation:** Owner request. Decisions taken with the owner: the model generates and code checks; the theme changes the browser UI only; candidates are shown as real window captures; `/settings` covers all welcome choices with a guided flow in the prompt.

## 4. Goals

- Goal 1: A theme = values for the UI's colour tokens plus a light/dark scheme, a name and a one-line rationale; stored and applied to the chrome UI on every start.
- Goal 2: Candidates from a free-text usability description, generated by the selected model (through `complete`) with built-in usability guidance, then contrast-checked and repaired in code.
- Goal 3: Each candidate shown as a real capture of the browser window in that theme; pick one to apply, or keep the current/system theme.
- Goal 4: A Theme step on the welcome page, and `/settings` (theme, model, page access, history access) guided by prompt suggestions.

## 5. Non-Goals

- Non-goal 1: Restyling web pages, or telling pages to prefer dark/light; pages stay as their sites made them.
- Non-goal 2: Font family, text size or spacing changes (text size stays Ctrl/Cmd + / −).
- Non-goal 3: Editing single colours by hand, importing/exporting themes, several saved themes.
- Non-goal 4: An assistant conversation that interviews the user; the flow is suggestions plus one description.

## 6. User Stories

- As a user with astigmatism, I type "a light theme suitable for astigmatism" and see a few calm light themes as screenshots, with why each helps, and pick one.
- As a user who finds bright screens painful, I ask for "dark, low glare" and get dark themes that avoid pure white text on pure black.
- As a user, I can change my theme, model and access settings later with `/settings`, guided by suggestions, without remembering each command.
- As a user, I can always go back to the system default theme.

## 7. Functional Requirements

1. **Theme model** (`appearance/shared/theme.ts`): `{ name, rationale, scheme: 'light' | 'dark', colors: Record<Token, '#rrggbb'> }` for every token listed in §3 (`--card-border` and `--hover` derived from `--text` with fixed alpha, so the model doesn't set alpha colours). Parsing rejects unknown tokens, non-hex values, names over 40 chars and rationales over 200 chars.
2. **Contrast rules** (WCAG 2.2, relative luminance per WCAG): text tokens (`--text`, `--muted`, `--error`, `--ok`, `--accent` used as text) ≥ 4.5:1 on `--panel-bg`, `--card-bg`, `--field-bg` and `--toolbar-bg`; `--accent-text` ≥ 4.5:1 on `--accent`; non-text (SC 1.4.11) `--focus` and `--field-border` ≥ 3:1 on the backgrounds they sit on; cloud colours ≥ 3:1 on `--card-bg`. A failing foreground is repaired by moving its lightness toward black or white (keeping hue) until it passes; a candidate that still fails is dropped. Each candidate reports its lowest text contrast ratio.
3. **Generation** (main): `appearance:generate(description)` (≤ 300 chars, trimmed, non-empty) asks the selected model once through agent's `complete`, with a system prompt that summarises usability guidance (WCAG AA/AAA contrast; astigmatism and halation: prefer light themes or dark grey, avoid pure white on pure black, avoid saturated thin accents; photophobia: dark, low luminance, no bright large areas; low vision: AAA contrast, strong focus ring; dyslexia: off-white/cream backgrounds, not pure white, softer contrast within AA; colour-vision deficiency: don't pair red/green for meaning, distinguish error/ok by lightness too) and asks for 3–4 candidates as JSON. Only the description and the token list are sent. Answers are parsed, repaired and filtered (rule 2); fewer than one valid candidate → an error the UI shows.
4. **Screenshots**: the picker hides itself behind a sample scene (a short page with a heading, body text, a link, a code line, buttons, an input and an error/ok line, in the page area beside the real assistant panel), applies each candidate in turn to the chrome UI, waits two frames, and asks main to capture the window (`appearance:capture`, the chrome UI's own webContents, scaled to ≤ 800 px wide JPEG). Then it restores the current theme and shows the screenshots in a gallery with name, rationale, scheme and lowest contrast ratio. The capture briefly shows each theme in the window (accepted).
5. **Choosing**: picking a screenshot applies and stores the theme (`appearance:set`); "Keep current" changes nothing; "System default" clears it (`appearance:set(null)`). Every chrome UI change is broadcast (`appearance:changed`); the stored theme is applied at start before first paint where possible (preload reads nothing; the UI applies it on mount).
6. **Welcome page**: a Theme step after Model: a text field with suggestion chips (light for astigmatism, dark with low glare, high contrast, dyslexia-friendly, colour-blind safe), "Show themes" runs requirements 3–5 inside the step; skipping keeps the system default. The step is a slot `App.tsx` fills with appearance's picker (welcome doesn't import appearance code).
7. **/settings** (prompt): `/settings` shows the current theme, model, page access and history access with how to change each. Nested suggestions: `/settings theme <need>` (the same five needs, or any typed text; `default` resets), `/settings model haiku|sonnet|opus`, `/settings page-access on|off`, `/settings history-access on|off`. `/settings theme <need>` opens the appearance page over the page area (like `/config`) with the description filled in and generation started; × or Escape closes it. The old `/model`, `/page-access`, `/history-access` keep working.
8. Errors (CLI missing, model failed, bad JSON, no valid candidate, capture failed) show in the picker with "Try again"; the current theme is never left half-applied.

## 8. Non-Functional Requirements

- Performance: generation is one model request (a few seconds); capturing 4 candidates takes under 2 s; nothing runs at startup except applying the stored theme.
- Reliability: a stored theme that fails parsing or contrast checks on load is ignored (system default), the file kept aside as `appearance.corrupt-*.json` by the JSON store.
- Security: new IPC `appearance:get|set|generate|capture|request-open` and `appearance:changed|open`; all arguments validated; `capture` returns only the chrome UI's own pixels (page views are hidden while the picker shows); model output is parsed as data (hex colours only), never used as CSS text. No web-content changes.
- Privacy: only the typed description goes to the model (through the user's Claude Code CLI); screenshots stay in memory in the chrome UI; `userData/appearance.json` holds the chosen theme.
- Accessibility: the gallery is a radio group with each screenshot's alt text naming the theme and its lowest contrast ratio; the sample scene and repaired themes meet WCAG AA; keyboard operable.
- Platforms: same everywhere; the OS dark/light preference only matters while no theme is stored.

## 9. UX / UI Notes

- User flow: welcome → … → Model → Theme ("What should the browser look like for you?") → chips or text → Show themes → brief flicker while capturing → gallery of 3–4 screenshots → pick → Next. Later: `/settings` → `theme` → pick a need or type one → same gallery over the page area.
- Visual considerations: gallery as a responsive grid of cards (screenshot, name, rationale, "Lowest contrast 7.2:1 · light"); the selected card outlined in the accent colour.
- Edge cases: the CLI not set up yet on the welcome page (error says to finish the Test step); the user resizes the window mid-capture (screenshots may differ in size, fine); hard-coded colours in the stylesheet that aren't tokens are moved to tokens where they affect readable text.

## 10. Technical Notes

- Proposed approach: new slice `src/features/appearance/` — `shared/theme.ts` (tokens, parsing, defaults), `shared/contrast.ts` (WCAG luminance, ratio, repair), `main.ts` (store, `generate` via agent's `complete`, `capture` via `ctx.window.webContents.capturePage` + `nativeImage.resize`, File → Appearance… opens the page), `ui/ThemeApplier.tsx` (applies the stored theme as inline custom properties on `document.documentElement` and `color-scheme`), `ui/ThemePicker.tsx` (description, generation, capture loop, gallery), `ui/AppearanceView.tsx` (the picker over the page area for `/settings theme`).
- Process split: main – store, model request, capture. UI – applying tokens, sample scene, gallery. IPC: `appearance:get|set|generate|capture|request-open` (UI → main), `appearance:changed|open` (main → UI).
- Dependencies: agent (`complete` from `main.ts`, `settings`/`updateSettings` for `/settings model|…` via `window.antimony.agent`), welcome (slot for the Theme step), prompt (`/settings` command and its suggestion tree). No new npm packages.
- Risks / unknowns: model JSON quality (strict parsing, repair, retry once on unparsable output); `capturePage` timing after a style change (two `requestAnimationFrame`s before capturing).

## 11. Acceptance Criteria

- [x] A stored theme is applied to the chrome UI at start and on change; "System default" restores the OS-driven palette.
- [x] Contrast checks follow WCAG 2.2 (luminance, 4.5:1 text, 3:1 non-text); failing colours are repaired or the candidate dropped; unit-tested with known ratios.
- [x] Generation sends only the description and token list to the selected model, parses strict JSON, and reports clear errors.
- [x] Each candidate is shown as a real capture of the window in that theme; afterwards the window is back in the current theme.
- [x] The welcome page has a Theme step that generates, shows and applies a theme, and can be skipped.
- [x] `/settings` shows current values; `/settings theme|model|page-access|history-access` are suggested level by level and work; `/settings theme <need>` opens the picker with the need filled in.
- [x] `npm run check` and `npm run test:e2e` pass; docs (appearance README, welcome and prompt READMEs, features index) updated.

## 12. Testing / Verification

- Manual test plan: welcome on a fresh profile with the real CLI: "a light theme suitable for astigmatism" → screenshots → pick → restart keeps it; `/settings theme dark, low glare`; `/settings theme default`.
- Automated test coverage: unit – contrast maths and repair, theme parsing, generation prompt/answer parsing (fake `complete`), store and IPC validation, ThemeApplier, ThemePicker flow (fake API), `/settings` command and suggestions; e2e – the fake CLI answers the theme request with fixed JSON; pick a candidate from the welcome step and see the chrome UI's `--panel-bg` change and persist across a relaunch.
- Regression considerations: OS dark mode without a stored theme; existing `/model`, `/page-access`, `/history-access`; the welcome step order.

## 13. Rollout / Follow-up

- Rollout plan: ships with the next build; nobody's look changes until they pick a theme.
- Follow-up work: text size and spacing in themes; page colour hints; sharing themes.

## 14. Changes during implementation

- Error and ok colours are not compared with each other by lightness; colour-vision guidance is in the model's instructions only, the code checks contrast.
- Stylesheet colours outside the tokens turned out to be shadows only, so no colours had to be moved into tokens.
- "Keep current" is simply not picking a candidate; the gallery offers the candidates and "Use system default".
- The welcome step's content is a `themeStep` slot that `App.tsx` fills with appearance's picker (welcome imports no appearance code); without the slot there is no Theme step.
- The sample theme used by tests lives in `appearance/shared/sample-theme.ts`, because main-process tests may not import renderer code.
- The e2e fake CLI answers the theme request with two fixed candidates. Checked by hand with the real Claude Code CLI: "a light theme suitable for astigmatism" gave four light themes (lowest text contrast 4.9–5.6:1) and real captures.
- Drafted ADR 0016 (Proposed) for generating themes with the model, checking them in code and showing window captures.
